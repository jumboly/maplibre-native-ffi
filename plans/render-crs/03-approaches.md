# 03. 実現アプローチの比較評価

「プラグイン形式が理想」という要件に対し、MapLibre Native
の現状（[01](01-maplibre-native-projection.md)）を踏まえた 5 案。

## 前提となる制約

- 投影法を差し替えられる拡張点は存在しない（`Projection` は
  static・非仮想、`TransformState` も非仮想）
- C++ には GL JS
  版のモンキーパッチ（実行時プロトタイプ差し替え）に相当する手段がない
- タイル→画面行列は現状アフィンのみだが、行列パイプライン自体はタイル毎 mat4
  に集約されており、**ホモグラフィに差し替えれば mercator
  シェーダのまま再投影できる**（GL JS 版で実証済み）

## 各案の補足

### A. 本格コア改造

`Projection::` 直呼び約 40 箇所、`TransformState`（1074 行）、`tile_cover` の
2^z 前提、`Tileset` への CRS フィールド追加、`SourceType` enum、style parser の
`projection` 対応まで波及する。上流には "Projector Component"
の構想（mdbook）があるが design-proposal も PR
も存在せず、マージには提案から始める必要がある。**E で実績を作ってから
A（上流提案）へ進む**のが現実的な順序。

### B. レイヤプラグイン

無改造で可能な唯一の形だが、実現できるのは「Mercator ベースマップ +
平面直角座標系で計算した独自オーバレイ」まで。本プロジェクトの目的（既存ベクトルタイル地図全体を平面直角座標系で出力）には届かない。`CustomDrawableLayer`
のタイル座標直渡し API（`custom_drawable_layer.cpp:557`）は E
の補助（方眼・トンボ描画など）に使える。

### C. 後処理ワープ

`mbgl-render` / `MapSnapshotter` で Mercator PNG +
ワールドファイルを出し、`gdalwarp -t_srs EPSG:6677`
で再投影する。実装ゼロで今日から動くため、**E
の受け入れ基準を作る比較リファレンス**として最初に整備する価値がある。ただし:
出力品質はラスタ再サンプリング依存（アンチエイリアス済みの線・ラベルが滲む)、ラベルの真北方向も
Mercator 基準のまま回転される。

### D. シェーダ差し替え

GPU 側だけ曲げても symbol 配置（`placement.cpp`）・collision・`tile_cover`
が追従しないため、E が必要とするフックの大半は結局必要になる。E
に対する優位性がない。

### E. 最小フック・パッチ（推奨）

GL JS 版の実測に基づく根拠:

- GL JS 版 `docs/04` は「fork した場合の本体変更は実質 2 ファイル 15〜20
  行」と評価。Native でも注入点は同程度に局所的（`matrixFor` 系 + symbol 投影 +
  tile_cover 視野）
- 差し替える機能の完全な一覧が GL JS
  版の上書きメソッド表として既にある（[02](02-vector-printer-reference.md) §2）
- 誤差解析・外部検証フィクスチャ・GIS 出力形式がそのまま流用できる

「プラグイン形式が理想」への回答としては: **純粋な外付けプラグインは現状の
Native では不可能。E
は「コアにはフック（機構）だけを置き、平面直角座標系の知識（ポリシー）は全て外部モジュールに置く」ことで、プラグイン形式に最も近づける案**であり、フック部分はそのまま上流
design-proposal（A への布石）にできる。

詳細設計は [04-recommended-design.md](04-recommended-design.md)。
